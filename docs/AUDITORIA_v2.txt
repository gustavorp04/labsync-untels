[CRÍTICO] C-2 · Token JWT en localStorage — vulnerable a XSS
────────────────────────────────────────────────────────────────────────────────
Archivos: LoginEstudiante.js, LoginDocente.js, LoginAdmin.js, LoginJefatura.js
          api.js

Sigue igual. localStorage es accesible desde cualquier script JS en la página.
Si un paquete npm comprometido o un input sin sanitizar ejecutan código XSS,
el token se puede robar y el atacante puede actuar como el usuario hasta que
el token expire (24 horas).

La solución definitiva es emitir el token como cookie httpOnly desde el
backend y eliminar todo acceso a localStorage para el token.

Nivel de urgencia: medio-alto en un sistema universitario real.
En contexto académico es aceptable documentarlo y moverlo a deuda técnica.

[MEDIO] M-1 · setTimeout sin cleanup en showToast (memory leak)
────────────────────────────────────────────────────────────────────────────────
Archivos: Estudiante.js línea 100-103
          Docente.js  línea 95-98

Código actual (idéntico en ambos):
  const showToast = (tipo, texto, dur = 5000) => {
    setToast({ tipo, texto });
    setTimeout(() => setToast(null), dur);  // ← timer huérfano
  };

Si el componente se desmonta antes de que pasen los 5 segundos (ej. el usuario
navega hacia otro lado), el setTimeout sigue ejecutándose e intenta actualizar
el estado de un componente ya desmontado. React imprime un warning y puede
causar comportamiento inesperado.

Corrección:
  Convertirlo en un hook que use useRef para guardar el ID del timer y
  limpiarlo en el cleanup:

  const toastTimerRef = useRef(null);
  const showToast = useCallback((tipo, texto, dur = 5000) => {
    if (toastTimerRef.current) clearTimeout(toastTimerRef.current);
    setToast({ tipo, texto });
    toastTimerRef.current = setTimeout(() => setToast(null), dur);
  }, []);
  useEffect(() => () => { if (toastTimerRef.current) clearTimeout(toastTimerRef.current); }, []);

[MEDIO] M-2 · Polling sin AbortController (requests huérfanos)
────────────────────────────────────────────────────────────────────────────────
Archivos: Estudiante.js (polling de equipos, paso 3, línea 154-198)
          Estudiante.js (polling de reservas, línea 122-140)
          Docente.js    (polling de equipos, paso 4, línea 123-169)
          Docente.js    (polling de reservas, línea 181-190)

El clearInterval evita que NUEVAS peticiones se lancen, pero si hay una
petición HTTP en vuelo cuando el componente se desmonta, esa petición llega
igual y llama a setActivos / setMisReservas sobre un componente ya desmontado.

Las peticiones se hacen a través de axios (api.js), que no cancela
automáticamente. Hay que pasar un AbortController.signal a cada fetch.

Corrección ejemplo para el polling de equipos:
  useEffect(() => {
    let intervalId = null;
    let abortCtrl = new AbortController();

    if (paso === 3 && labSel && horarioSel) {
      const cargarEquipos = async (showLoading = false) => {
        if (showLoading) setLoading(true);
        try {
          const data = await laboratorioService.getActivosPorLab(
            labSel.id_laboratorio,
            horarioSel.id_horario,
            { signal: abortCtrl.signal }  // ← pasar a axios
          );
          setActivos(data);
          // ... resto de lógica
        } catch (err) {
          if (err.name !== 'CanceledError') console.error(err);
        } finally {
          if (showLoading) setLoading(false);
        }
      };
      cargarEquipos(true);
      intervalId = setInterval(() => cargarEquipos(false), 3000);
    }

    return () => {
      if (intervalId) clearInterval(intervalId);
      abortCtrl.abort();  // ← cancelar petición en vuelo
    };
  }, [paso, labSel, horarioSel]);

O usar el sistema feedbackMsg ya existente en Admin.js (que sí se muestra):
  catch (error) {
    setFeedbackMsg({ tipo: 'error', texto: 'Error al cargar reservas.' });
  }

[BAJO] M-4 · Clave userId duplicada en localStorage
────────────────────────────────────────────────────────────────────────────────
Archivos: Estudiante.js línea 82
          Admin.js     línea 255
          Docente.js   línea 87

Estudiante.js:
  const userId = localStorage.getItem("userId") || localStorage.getItem("id_usuario") || "";

Admin.js:
  const adminId = localStorage.getItem('userId') || localStorage.getItem('id_usuario');

Docente.js:
  const userId = localStorage.getItem("id_usuario") || "";

Hay dos claves distintas para el mismo dato (id del usuario). Estudiante y
Admin usan ambas como fallback porque no están seguros de cuál login guardó
qué clave. Docente asume siempre "id_usuario". Si un login guarda "userId"
y el componente Docente lee "id_usuario", las llamadas fallarán silenciosamente
(userId queda vacío y la petición va a /api/v1/usuarios//reservas/).

Corrección: estandarizar a una sola clave en todos los logins y componentes.
  Valor recomendado: "id_usuario" (ya es el más usado y coincide con el modelo).

[ALTO] N-1 · CrearReservaSerializer aún usa la lógica "día siguiente" (inconsistencia)
────────────────────────────────────────────────────────────────────────────────
Archivo: backend/reservas/serializers/reserva_serializers.py línea 23-26

  # Primera capa de validación (serializer)
  manana = timezone.localtime(timezone.now()).date() + timedelta(days=1)
  if fecha_reserva < manana:
      raise serializers.ValidationError("La reserva debe realizarse con al menos 1 día de anticipación.")

Esta validación es la primera que ve el docente (antes de que el service
la valide). Usa la lógica old de "fecha < mañana" que ya se corrigió en el
service. Resultado:

  Escenario:  hoy es lunes 26 a las 23:50
              el docente intenta reservar para martes 27 a las 00:05 (15 min)

  Serializer: PASA (fecha no es menor que mañana)
  Service:    BLOQUEA correctamente (solo 15 min de diferencia < 24h)

El usuario recibe el mensaje genérico del service, no el del serializer, así
que el bloqueo funciona. Pero el mensaje de error es confuso porque el
serializer no lo detectó y el service usa un mensaje diferente.

Corrección: replicar la misma lógica de datetime exacto en el serializer:
  from datetime import datetime as dt_datetime
  ahora = timezone.now()
  naive_inicio = dt_datetime.combine(horario.fecha, horario.hora_inicio)
  fecha_hora_inicio = timezone.make_aware(naive_inicio, timezone.get_current_timezone())
  if (fecha_hora_inicio - ahora) < timedelta(hours=24):
      raise serializers.ValidationError("La reserva debe hacerse con al menos 24 horas de anticipación.")

[ALTO] N-2 · HorarioDisponibleSerializer.get_es_reservable usa lógica "día siguiente"
────────────────────────────────────────────────────────────────────────────────
Archivo: backend/reservas/serializers/reserva_serializers.py línea 107-108

  def get_es_reservable(self, obj):
      manana = timezone.localtime(timezone.now()).date() + timedelta(days=1)
      return obj.fecha >= manana

Este campo controla si el botón de horario aparece habilitado o bloqueado
en el stepper de Estudiante.js y Docente.js.

Problema: Si hoy es lunes 26 a las 23:55 y existe un horario para martes
27 a las 00:10, el serializer devuelve es_reservable=True (la fecha es
"mañana o después"). El estudiante ve el botón habilitado, hace clic, y
recibe un error del backend: "menos de 24h de anticipación".

El bloqueo correcto se produce en el service, pero la UX es mala porque
el usuario navegó hasta el paso 3 para recibir un error.

Corrección: misma lógica de datetime exacto:
  def get_es_reservable(self, obj):
      from datetime import datetime as dt_datetime
      ahora = timezone.now()
      naive_inicio = dt_datetime.combine(obj.fecha, obj.hora_inicio)
      fecha_hora_inicio = timezone.make_aware(naive_inicio, timezone.get_current_timezone())
      return (fecha_hora_inicio - ahora) >= timedelta(hours=24)

  Asegurarse de importar: from datetime import timedelta, datetime as dt_datetime

[MEDIO] N-4 · N+1 en HorarioDisponibleSerializer (horarios_por_laboratorio)
────────────────────────────────────────────────────────────────────────────────
Archivo: backend/reservas/views/reserva_views.py (función horarios_por_laboratorio)

  horarios = HorarioDisponible.objects.filter(
      id_laboratorio=id_laboratorio,
      ...
  ).order_by('fecha', 'hora_inicio')

  serializer = HorarioDisponibleSerializer(horarios, many=True)

HorarioDisponibleSerializer accede a:
  - obj.id_laboratorio.id_tipo.nombre   → 2 queries FK por cada horario
  - obj.id_laboratorio.aforo_maximo     → misma relación (Django cachea el

      id_laboratorio=id_laboratorio,
      ...
  ).select_related('id_laboratorio', 'id_laboratorio__id_tipo').order_by(...)
