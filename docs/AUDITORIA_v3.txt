[P-1] 🔴 CRÍTICO — DJANGO_DEBUG defaultea 'True' → cookies cross-origin rotas
─────────────────────────────────────────────────────────────────────────────
Archivo:   backend/config/settings.py  línea 26
Archivo:   backend/Dockerfile

Error observado en producción:
  GET https://labsync-backend-90371338218.us-central1.run.app/api/v1/usuarios/12/reservas/
  → 403 Forbidden (AxiosError)

DIAGNÓSTICO:

  settings.py línea 26:
    DEBUG = os.environ.get('DJANGO_DEBUG', 'True') == 'True'
                                             ^^^^^^
                                             DEFAULT ES 'True'  ← EL PROBLEMA

  El Dockerfile NO establece DJANGO_DEBUG=False:
    ENV PYTHONDONTWRITEBYTECODE 1
    ENV PYTHONUNBUFFERED 1
    # ← No hay DJANGO_DEBUG aquí

  Cloud Run tampoco lo hereda a menos que esté en la consola GCP como
  variable de entorno explícita.

  Consecuencia directa: en producción DEBUG=True, entonces:

    auth_views.py:
      is_prod = not django_settings.DEBUG   ← False (porque DEBUG=True)

    response.set_cookie(
        key='auth_token',
        samesite='None' if is_prod else 'Lax',   ← 'Lax' en producción ← ERROR
        secure=is_prod,                           ←  False en producción ← ERROR
    )

  Una cookie SameSite=Lax + Secure=False NO es enviada por el navegador
  en peticiones cross-origin (Vercel → GCP Cloud Run).
  El backend no recibe ningún token → CustomTokenAuthentication retorna None
  → IsAuthenticated falla → Django REST Framework responde 403.

CORRECCIÓN (2 cambios):

  1. settings.py — cambiar el default a 'False':
     ────────────────────────────────────────────
     ANTES: DEBUG = os.environ.get('DJANGO_DEBUG', 'True') == 'True'
     DESPUÉS: DEBUG = os.environ.get('DJANGO_DEBUG', 'False') == 'True'

  2. Dockerfile — añadir la variable explícita:
     ────────────────────────────────────────────
     ENV PYTHONDONTWRITEBYTECODE 1
     ENV PYTHONUNBUFFERED 1
     ENV DJANGO_DEBUG False    ← AÑADIR ESTA LÍNEA

  NOTA: Si DJANGO_DEBUG está seteada a 'True' en la consola de Cloud Run
  como variable de entorno, también hay que cambiarla ahí a 'False'.

  NOTA 2: Este fix requiere redeploy del backend en Cloud Run para tomar efecto.
  Después del redeploy, los usuarios actuales necesitan cerrar sesión y volver
  a ingresar (para obtener una nueva cookie SameSite=None; Secure=True).

[A-1] 🟠 ALTO — api.js solo intercepta 401; el 403 deja la UI rota
─────────────────────────────────────────────────────────────────────────────
Archivo: frontend/src/services/api.js  líneas 31-43

  El interceptor de respuesta solo redirige al login cuando hay 401:
    if (error.response && error.response.status === 401) {
      ...
      window.location.href = '/';
    }

  Pero IsAuthenticated de DRF devuelve 403 (no 401) cuando no hay ningún
  autenticador que haya reclamado la solicitud (retorno None).
  Resultado: cuando el cookie falta (sesión expirada, otro dispositivo,
  etc.), el usuario ve una pantalla rota con errores de consola, en vez
  de ser redirigido al login automáticamente.

CORRECCIÓN:
  api.js interceptor — extender a 403 con condición de sesión:
  ─────────────────────────────────────────────────────────────
  (error) => {
    const status = error.response?.status;
    if (status === 401 || (status === 403 && !localStorage.getItem('id_usuario'))) {
      const theme = localStorage.getItem('app-theme');
      localStorage.clear();
      if (theme) localStorage.setItem('app-theme', theme);
      window.location.href = '/';
    }
    return Promise.reject(error);
  }

  La condición "!localStorage.getItem('id_usuario')" distingue entre:
  - 403 de sesión expirada (redirect al login) ← usuario no logueado
  - 403 de permisos reales ("no tienes rol de admin") ← no redirigir
